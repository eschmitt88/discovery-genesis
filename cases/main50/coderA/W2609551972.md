## Reasoning
The abstract frames the update entirely in terms of newly available or newly integrated algorithmic capabilities driving improved predictions, which is the means-first pattern (capability -> observation/output -> claim) rather than the same capability being applied to a new target. `instrument` is the central label since the contribution is fundamentally a software tool; `recombination` is kept as a second label because the update's substance is explicitly assembling several independently developed external algorithms (CASSIS, DIAMOND, RODEO) into one platform, which removing would understate — the improvement is not one new algorithm but several combined into the pipeline.

## Alternative reading
problem-first is a real alternative under the codebook's "serial reuse of the authors' own established platform" rule — antiSMASH itself is cited to the authors' own 2011/2013/2015 versions (a 4x-citation pattern matching the codebook's explicit tell), and one could read this as simply "the next version" of a maintained resource rather than a capability-driven discovery. I lean means-first because, unlike the "next gene/next species" pattern, the target here (BGC prediction generally) is unchanged — what changed is the prediction *method* itself (new algorithms), which is the capability-new-to-the-tool case the v1.1 rule distinguishes from serial target reuse.

## Notes for the codebook
This is a genuinely hard case for the "authors' own platform, tell = 4-8x self-citation" rule: the tell is present (antiSMASH cited to itself across versions) but the paper is not "next target," it is "next capability release" of a maintained tool. The codebook's worked examples (next gene, next cancer type, next species) are all next-*target* cases; a versioned-software-tool case like this one is a distinct pattern (next-*capability*-release-of-a-maintained-platform) that arguably deserves its own tell/example, since the two point to opposite genesis_model answers.
